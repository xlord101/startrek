This is a solid, clean real-world workflow. Structuring this module-by-module is exactly the right approach to keep the development organized and prevent scope creep.

Since the goal is a responsive web application that functions flawlessly on both desktop (for main/office admins) and mobile viewports (for field supervisors on Android/iOS), Next.js paired with a robust relational database is an excellent architectural choice.

Here is the architectural blueprint, database design, and tech stack configuration specifically tailored for Module 1: The Procurement Process.

🛠️ The Recommended Tech Stack
Frontend & Backend Framework: Next.js (App Router). It provides server-side rendering for administrative dashboards and fast, client-side interactions for field workers. It easily builds into a mobile-friendly Progressive Web App (PWA) or can be wrapped later using tools like Capacitor if a native app shell is required.

Database: PostgreSQL. The data structured here (Farmers → Tasks → Supervisors → Particulars) is highly relational. PostgreSQL ensures strict data integrity, which is vital when handling financial rates, tonnage weights, and audit trails.

Database ORM: Prisma or Drizzle ORM. This makes writing migrations and managing relations straightforward with full type safety.

Authentication: Auth.js (NextAuth). Perfect for implementing the required Role-Based Access Control (RBAC) to ensure strict downward data flow.

Styling: Tailwind CSS + Shadcn UI / Radix UI. Highly responsive, clean layouts that optimize quickly for mobile screens.

🗄️ Database Schema Design (Procurement Module)
To support the exact requirements you mentioned—such as retaining a historical list of farmers for dropdowns, managing multiple box particulars per visit, and tracking who approved the rates—here is the proposed relational structure.

1. User Table (Admins & Supervisors)
Tracks the internal team members and their specific authorization levels.

id (UUID, Primary Key)

name (String)

email (String, Unique)

password_hash (String)

role (Enum: MAIN_ADMIN, OFFICE_ADMIN, SUPERVISOR)

is_active (Boolean)

2. Farmer Table
Maintains a clean history of every farmer who has ever called in, preventing duplicate entries and feeding the administrative dropdowns.

id (UUID, Primary Key)

name (String)

mobile_number (String, Unique)

address (Text)

3. ProcurementTask Table
The core operational table that moves through the states of the procurement workflow.

id (UUID, Primary Key)

farmer_id (ForeignKey linking to Farmer)

approx_tonnage (Decimal)

status (Enum: PENDING_ASSIGNMENT, ASSIGNED_TO_SUPERVISOR, FIELD_SUBMITTED, APPROVED)

supervisor_id (ForeignKey linking to User, Nullable until assigned)

assigned_at (Timestamp, Nullable)

// Field Supervisor Inspection Data (Filled during site visit)

actual_tonnage (Decimal, Nullable)

ratio_percentage (Decimal, Nullable)

quality (Enum: EXCELLENT, GOOD, AVERAGE, REJECT, Nullable)

rejection_reason (Text, Nullable)

supervisor_submitted_at (Timestamp, Nullable)

// Final Approval Data

final_rate (Decimal, Nullable)

approved_by_id (ForeignKey linking to User, Nullable)

approved_at (Timestamp, Nullable)

4. TaskParticulars Table
Because a single farm might yield multiple box categories (5kg, 7kg, 13kg, etc.) during a single inspection, this one-to-many relationship handles the dynamic "add another particular" button.

id (UUID, Primary Key)

task_id (ForeignKey linking to ProcurementTask)

box_type (Enum: 5KG, 7KG, 13KG, 13_5KG, 16KG)

🔁 Step-by-Step Module Flow Implementation
Step 1: Inbound Call & Farmer Registration
UI/UX: A simple, high-speed data entry form for the Office Admin.

Logic: When typing a farmer's name, an autocomplete dropdown queries the Farmer table. If it's a new farmer, the form creates a new Farmer record and initializes a ProcurementTask marked as PENDING_ASSIGNMENT.

Step 2: Supervisor Allocation
UI/UX: A dashboard view displaying all PENDING_ASSIGNMENT tasks. Clicking a row opens the editable details alongside a clean dropdown populated with users whose role is SUPERVISOR.

Logic: Saving this form updates the task status to ASSIGNED_TO_SUPERVISOR and sets the supervisor_id.

Step 3: Field Inspection & WhatsApp Integration
UI/UX: When a Supervisor logs in, the system checks their User ID and filters the view exclusively to tasks where supervisor_id == current_user.id. The mobile layout features large, fat-finger-friendly inputs for field conditions.

Logic: The "Submit" button remains disabled until all mandatory fields are verified.

WhatsApp Text Formatting: Upon successful submission to the database, the frontend intercept triggers a browser-native redirection string using the WhatsApp API:

JavaScript
const whatsappText = encodeURIComponent(
  `*Procurement Report*\nFarmer: ${task.farmer_name}\nActual Tons: ${formData.actual_tonnage}\nQuality: ${formData.quality}`
);
window.open(`https://wa.me/?text=${whatsappText}`, '_blank');
Step 4: Verification & Rate Finalization
UI/UX: The task reappears on the Main/Office Admin dashboards under a "Pending Approval" column.

Logic: The Admin reviews the supervisor's numbers, inputs or modifies the final_rate, and hits confirm. The system stamps the approved_by_id field. If an Office Admin completes it, the UI explicitly flags the record label as "Accepted by Office". The record status updates to APPROVED and automatically locks down, becoming read-only for this module and exposing it to the upcoming harvesting module.

# Project: Startrek - System Architecture & Workflow

## Overview
"Startrek" is a responsive web application for agricultural supply chain management. It tracks the lifecycle of produce from initial farmer intake (procurement), through field inspection, harvesting, cold storage, and final container dispatch. 

## Tech Stack
*   **Framework:** Next.js (App Router)
*   **Database:** PostgreSQL (with Prisma or Drizzle ORM)
*   **Styling:** Tailwind CSS + Shadcn UI
*   **Authentication:** NextAuth (Role-Based Access Control)
*   **Target Devices:** Desktop (for Admins/Office Staff) and Mobile (for Field Supervisors).

## Role-Based Access Control (RBAC)
Strict downward data flow. Lower levels cannot access higher-level information.
1.  **Main Admin:** Full system access. Can add/remove supervisors and override rates.
2.  **Office Admin:** Dashboard access. Handles intake, assigns tasks, approves procurement rates.
3.  **Field Supervisor:** Mobile-optimized access. Only sees tasks assigned specifically to them.
4.  **Inventory Admin:** Access to warehouse intake and box tracking.
5.  **Cold Storage Admin:** Access to storage room allocation and dispatch verification.

---

## Module 1: Procurement Process (First Priority)

### 1.1 Inbound Order Intake (Desktop)
*   **Actor:** Office Admin / Main Admin
*   **Action:** When yield information is received (via any medium), the admin fills out an intake form.
*   **Data Fields:**
    *   Farmer Name (Searchable dropdown linked to DB. If new, creates a new record).
    *   Address
    *   Mobile Number
    *   Approximate Tonnage of Field
*   **Outcome:** Saves to database as a new task with status `PENDING_ASSIGNMENT`.

### 1.2 Supervisor Allocation (Desktop)
*   **Actor:** Office Admin / Main Admin
*   **Action:** Admin views a list of `PENDING_ASSIGNMENT` tasks. 
*   **Data Fields:**
    *   Admin selects a task, bringing up the editable intake information.
    *   Selects a supervisor from a dropdown list of active `Supervisor` users.
*   **Outcome:** Task status updates to `ASSIGNED`. Task now appears on the selected Supervisor's dashboard.

### 1.3 Field Inspection & Verification (Mobile-Optimized)
*   **Actor:** Field Supervisor
*   **Action:** Supervisor travels to the site, views their assigned task, and fills out the actual verification form. Form cannot be submitted until required fields are filled.
*   **Data Fields:**
    *   Editable: Name, Address, Number, Alternate Number.
    *   Box Particulars: Dropdown (`5kg`, `7kg`, `13kg`, `13.5kg`, `16kg`). Must include a dynamic "Add Another Particular" button to allow multiple box types per farm.
    *   Actual Tonnage
    *   Ratio (%)
    *   Quality: Dropdown (`Excellent`, `Good`, `Average`, `Reject`). If `Reject` is selected, a mandatory text box for "Reason" appears.
    *   Rate: (Optional field).
*   **Outcome:** Task status updates to `FIELD_SUBMITTED`. 
*   **Trigger:** On successful submit, format the form details into a text block and trigger a WhatsApp share link (`wa.me`) to post the update to the team group.

### 1.4 Final Approval & Lockdown (Desktop)
*   **Actor:** Office Admin / Main Admin
*   **Action:** Admin reviews the `FIELD_SUBMITTED` data. 
*   **Data Fields:**
    *   If the rate was not filled on-site, the Admin inputs the final rate here.
    *   If already filled, the Admin has the authority to edit/override it.
*   **Outcome:** Admin submits. Record is stamped with "Accepted by [Admin Name/Role]". Task status changes to `APPROVED_PROCUREMENT`. It is now locked and feeds into the Harvesting Module list.

---

## Module 2: Harvesting (Upcoming)

### 2.1 Harvesting Allocation
*   **Data Source:** Pulls from the `APPROVED_PROCUREMENT` list.
*   **Action:** Admin assigns a Supervisor for the harvest.
*   **Parameters:** Box Type, Brand, Vehicle Selection, Labor Contact, Team (dropdown of 10 teams), Priority level.

### 2.2 Harvest Execution (Mobile)
*   **Action:** Supervisor accepts task.
*   **Features:**
    *   Work start timestamp (updates via WhatsApp).
    *   Automated ping/reminder every 2 hours asking for an update on "quantity of boxes done".
    *   Record empty quantity of boxes loaded (subtracts from available inventory).
    *   Perform quality checks.
    *   On completion: Submit total quantity, generate procurement bill (fetching existing data + wastage), and share to WhatsApp.

### 2.3 Dispatch & Inventory Return
*   **Action:** Vehicle dispatched to Cold Storage.
*   **Inventory Logic:** Supervisor logs remaining unused boxes. Inventory Admin verifies the return. `(Used Boxes = Loaded Boxes - Remaining Boxes - Wastage)`.

---

## Module 3: Cold Storage & Fulfillment (Upcoming)

### 3.1 Receiving
*   **Action:** Cold Storage Admin receives dispatch notification and procurement bill. Cross-verifies total boxes received.

### 3.2 Storage Allocation
*   **Action:** Admin submits box locations, adding multiple brands to specific Room Numbers (via dropdown).

### 3.3 Container Booking & Dispatch
*   **Action:** Log Order/Invoice Number and Container Details. Send packing instructions to Inventory and Cold Storage. Track statuses: `Loading Started`, `Sealed`, `Dispatched`, `Completed`.
